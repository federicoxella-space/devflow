# Pannello del flusso devflow — piano di implementazione

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** una mod dentro il plugin devflow che disegna nella desktop app la linea verticale delle fasi di `/devflow:factory`, con agenti live, rientri, riepilogo del board e notifiche "tocca a te".

**Architecture:** moduli puri e testati (parsing di board e file di feature, modello del flusso, palette, SVG, notifiche) più un `register.tsx` che li collega agli eventi della mod (`agent.spawn`, `tool.call`, `turn.step`, `turn.complete`, `ui.render`). Stato della run in `$.state` (sessione), tempi per fase in `$.store` (tra sessioni). Deduzione passiva: l'orchestratore non cambia.

**Tech Stack:** mod di Claude Code (TypeScript/TSX, API `claude-code`, test con `claude-code/testing` e `claude plugin test`). Riferimento di stile e struttura: `F:\claude-agent-monitor\hooks`.

**Spec:** `docs/superpowers/specs/2026-10-27-flow-pane-design.md` (mockup: `2026-10-27-flow-pane-mockup.svg`)

## Global Constraints

- Il pannello è attivo solo se esiste `factory/config.md` nella root della sessione; altrove nessun hook fa nulla oltre a `next(e)`.
- Solo la sessione corrente: nessun watch o polling di `factory/`.
- La fase anima solo mentre `/devflow:factory` gira in questa sessione; una riga del board ferma senza orchestratore è mostrata nel riepilogo come "ferma in `<stato>`".
- Card e conteggio "agenti attivi" solo per `subagentType` che inizia con `devflow:`.
- Colori modello (scuro / chiaro): fable `#F59E0B`/`#B45309`, mythos `#22D3EE`/`#0891B2`, opus `#A78BFA`/`#7C3AED`, sonnet `#34D399`/`#059669`, haiku `#60A5FA`/`#2563EB`, altro `#9A8F85`/`#7A7068`.
- Stati: fatto sabbia `#C9B79C`/`#8A7458` pieno; in corso bianco caldo `#EDE6DE`/`#211E1B` pieno con alone che si espande; tocca a te contorno bianco che pulsa in scala (`values="1;1.3;1"`, 0.9s); da fare contorno grigio `#9A8F85`/`#7A7068`.
- Esiti: pass lime `#A3E635`/`#4D7C0F`; rientro e CHANGES rosso `#EF4444`/`#DC2626`; sempre con ✓/✕.
- Testo: `#E5DED6`/`#3D3833`, muted `#9A8F85`/`#7A7068`, linee `#3A3532`/`#D6CEC6`, fondo card `#262322`/`#FBF9F6`; l'SVG non dipinge uno sfondo proprio.
- Font monospace `ui-monospace,'Cascadia Code',Consolas,monospace`; esagoni come agent-monitor.
- Freccia di rientro: termina all'altezza del centro dell'esagono della fase di destinazione; `stroke-dashoffset` da `0` a `-22` (scorre verso la punta).
- `Svg` con `isInteractive: true`, `source` ≤ 131072 caratteri, `alt` sempre valorizzato.
- Notifica: `$.ui.toast(text)` + `$.ui.notify(text, { title: 'devflow · <id>' })`, una volta per evento.
- Testi in italiano e inglese (`userConfig.language`: `auto` | `it` | `en`, come agent-monitor).
- Nessun token o costo nel pannello.

## Review Focus

1. **Board modificato a mano o malformato** (righe mancanti, colonne vuote, stato sconosciuto): il pannello mostra quello che capisce e non lancia mai; uno stato sconosciuto va nel riepilogo come testo grezzo. → test in Task 3.
2. **`/devflow:factory` interrotto (Esc) o fallito a metà**: al `turn.complete` del loop principale la run smette di animare; agenti rimasti `running` non tengono la fase "in corso". → test in Task 5.
3. **Agente che finisce con `failed`/`killed`**: la card sparisce dalla fase attiva e non resta un timer che corre. → test in Task 5.
4. **Molti agenti in parallelo (es. 8 coder)**: il `source` resta sotto 131072 caratteri e l'altezza cresce in modo lineare; descrizioni lunghe sono troncate con `…`. → test in Task 6.
5. **Testo con `<`, `&`, `"` in task, motivi e titoli feature**: sempre con escape nell'SVG. → test in Task 6.

### Task 5: Modello del flusso

Il cuore: dato lo stato raccolto dagli eventi, cosa mostra ogni fase.

**Files:**
- Create: `hooks/flow.ts`, `hooks/flow.test.ts`
- Modify: `types/index.d.ts`

**Interfaces:**
- Consumes: `BoardRow` (Task 3), `ReviewResult`, `GateResult` (Task 4), `Family`, `family` (Task 2)
- Produces:
  - `const PHASES = ['interview', 'spec', 'build', 'gate', 'commit', 'review', 'approver', 'finish'] as const`; `type PhaseId = typeof PHASES[number]`
  - `type PhaseStatus = 'done' | 'active' | 'waiting' | 'todo'`
  - `type AgentCard = { id: string; type: string; description: string; model?: string; effort?: string; startedAt: number; endedAt?: number; status: 'running' | 'done' | 'failed'; activity: string; escalatedFrom?: string }` (`type` senza prefisso `devflow:`)
  - `type Run = { featureId?: string; active: boolean; startedAt: number; waiting: boolean; gateRunning: boolean; phaseStarted: Partial<Record<PhaseId, number>>; phaseEnded: Partial<Record<PhaseId, number>>; questions: number }`
  - `PluginState['devflow'] = { run: Run; agents: Record<string, AgentCard> }`
  - `phaseOfAgent(type: string): PhaseId | undefined` — `spec-writer`→spec, `coder`/`builder`→build, `committer`→commit, `review-*`→review, `approver`→approver
  - `phaseOfState(state: string): PhaseId | undefined` — interview→interview, spec/spec-review→spec, build→build, review→review, approve→approver, pr-open→finish
  - `type FlowView = { featureId: string; title: string; branch: string; round: number; maxRounds: number; elapsedMs: number; phases: { id: PhaseId; status: PhaseStatus; durationMs?: number; agents: AgentCard[] }[]; reentry?: { from: PhaseId; to: PhaseId; reason: string }; reviews: ReviewResult[]; gate?: GateResult }`
  - `deriveView(input: { run: Run; row: BoardRow; agents: AgentCard[]; reviews: ReviewResult[]; gates: GateResult[]; maxRounds: number; now: number }): FlowView`

Regole di `deriveView` (sono decisioni, non deducibili dai tipi):
- Fase attiva: quella del tipo di agente `running` più avanzata in `PHASES`; se nessuno gira, `gate` se `run.gateRunning`, altrimenti `phaseOfState(row.state)`. Se `!run.active`, nessuna fase è `active` né `waiting` (diventa `todo` o `done` dal board).
- Fasi prima dell'attiva → `done`; dopo → `todo`. `finish` è `waiting` se `run.waiting` e lo stato è `approve`; in `interview`/`spec-review` con `run.waiting` la fase attiva diventa `waiting`.
- `approver` è `done` quando il suo agente è `done`, anche con board ancora in `approve`.
- Rientro: con `row.round > 1` e fase attiva `build`, `reentry` = dalla review del round precedente se una `ReviewResult` di `round - 1` è `CHANGES` (`reason` = `"<reviewer>: <reason>"`), altrimenti dal gate del round corrente se `pass: false`.
- Escalation: un `builder` creato mentre un `coder` dello stesso `description` è finito nel round corrente riceve `escalatedFrom: 'coder'` (fatto in Task 8 all'`agent.spawn`; qui solo il tipo).
- Agenti mostrati: solo `status: 'running'` nella fase attiva; `done`/`failed` non compaiono.
- `durationMs` = `phaseEnded − phaseStarted` se entrambi presenti.

### Task 8: Collegamento agli eventi e pannello desktop

**Files:**
- Create: `hooks/register.tsx`, `hooks/register.test.tsx`

**Interfaces:**
- Consumes: tutto quanto sopra.
- Produces: pane `devflow-flow`, comando `devflow-panel` (se il motore accetta un nome con `:` o il prefisso del plugin, usare quello; altrimenti `devflow-panel`).

Eventi (ognuno chiama sempre `next(e)`; se la mod non è attiva fa solo quello):
- `session.start`: attiva se `$.fs.exists('factory/config.md')`; legge `max_rounds` dal frontmatter di `config.md` (default 2); lingua; `$.command.register`; `$.clock.every(1000)` che invalida il pane solo se c'è un agente `running`; azzera `run.active`.
- `tool.call` sul loop principale:
  - `Skill` con skill `devflow:factory` → `run.active = true`, `startedAt`, rilegge il board, `$.ui.open` del pane alla prima volta della sessione.
  - `Write`/`Edit` su un path che finisce con `factory/board.md` → dopo `next`, rilegge il board, aggiorna `phaseStarted`/`phaseEnded` della feature al cambio di stato (persistiti in `$.store` con chiave `times:<featureId>`), chiama `onBoardChange` e notifica se nuovo.
  - `Bash` il cui `command` coincide con uno dei comandi `build`/`lint`/`test` di `config.md` → `gateRunning` vero fino al ritorno di `next`.
  - `AskUserQuestion` con `run.active` → `run.waiting = true`, `onQuestion` + notifica, `questions++` se in `interview`; dopo `next` → `waiting = false`.
- `tool.call` con `agentId` di una card → `activity` = descrizione breve dello strumento (riusa la forma `describeTool` di agent-monitor: `Edit <path>`, `Bash <comando>`).
- `agent.spawn` con `subagentType` `devflow:*` → crea la card dopo `next` (id da `r.agentId`, modello da `r.model`); escalation come da Task 5.
- `turn.step` con `agentId` di una card → `model`/`effort` effettivi, `activity = '@thinking'` prima di `next`.
- `turn.complete`: con `agentId` di una card → `done`/`failed` ed `endedAt`; senza `agentId` (loop principale) mentre `run.active` → `run.active = false`, `waiting = false`.
- `ui.render` `{ component: 'Pane', requestId: 'devflow-flow' }`: su desktop/vscode/mobile, con run attiva e una riga del board per `run.featureId` → `<Svg isInteractive source={flowSvg(...).source} alt={flowAlt(...)} width height />`; altrimenti `boardSvg`. Larghezza = `bodyColumns × 7.8` (come agent-monitor `CELL_W`), minimo 360. Modalità palette: `auto` o `config` secondo l'esito del Task 1 (con `config`: `dark`/`light` da `theme` di `$.config.list()`, `auto` se assente). Gate e review letti con `$.fs.list`/`$.fs.read` da `factory/features/<id>/` a ogni render (piccoli; nessuna cache).
- `command.run` `devflow-panel` → apre il pane se chiuso, lo chiude se aperto (`$.ui.panes()`).
